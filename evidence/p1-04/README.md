## 2. 捕获源身份探测（只读，不产生像素）

用 `thumbnailSize: 0x0` 枚举捕获源，**不渲染任何帧**（实测 `hasThumbnail=false`），因此本探测不产生像素、不落盘。

| 事实 | 实测 |
|---|---|
| 窗口源 id 形状 | `window:<hwnd>:<index>`，如 `window:329270:0` |
| **中间段是真实 Win32 窗口句柄** | 用 `IsWindow` 验证 `329270` 与 `1181646` 均为存活窗口，且标题与源名一致（`pi-orb - Pi Web - Google Chrome`、`Backstop Window`） |
| 屏幕源形状 | `screen:0:0`（`screen:<monitor>:<index>`） |
| 显示器 | 1 个，`scaleFactor=1.5`（与 P0-04 的 150% 缩放一致） |

**设计后果**：按**原生句柄**匹配目标窗口，而不是按标题。标题匹配会有歧义（同名窗口）且窗口改名即失效；句柄是精确身份。`matchWindowSource` 要求前缀 `window:<handle>:` 完全匹配，因此 `window:32927:` 不会误匹配 `window:329270:0`，`screen:...` 也永远不会被当成窗口。

## 3. 授权与拒绝路径实测

链路真实：真实 Electron 主进程 → 真实本地 helper → 真实 pi-web（固定 HEAD）→ 本机假 provider（记录每个请求体）。无真实模型、无真实凭据。

### 3.1 目标记录与 DPI（P0-04 的硬要求）

| 断言 | 实测 |
|---|---|
| helper 运行并返回 JSON | 通过 |
| **显式声明 per-monitor-v2 DPI 感知且实际生效** | `isPerMonitorV2=true`、`setCallSucceeded=true`、`isPerMonitorV1=false`、`isUnaware=false` |
| helper 耗时 | 约 746 ms（记录为成本事实） |

> 注意实现细节：`GetAwarenessFromDpiAwarenessContext` 会把 v1 与 v2 **都返回 2**，因此判断 v2 必须用 `AreDpiAwarenessContextsEqual`。仅看枚举值会漏判——这正是 P0-04 要求"必须显式声明"的那条。

### 3.2 无目标窗口 → 拒绝，且**不上传任何东西**

| 断言 | 实测 |
|---|---|
| 无目标窗口时拒绝截图 | `ok=false` |
| 拒绝理由说明"目标在获得焦点前记录" | 通过 |
| **拒绝理由不提供整屏兜底** | 通过（不含 whole/full/entire screen） |
| **被拒绝的截图没有产生任何模型调用** | `before=0 after=0` |
| 伪造的确认不发任何东西 | `sent=false` |
| 该伪造确认也没有产生模型调用 | `before=0 after=0` |
| 无待确认时丢弃是幂等的 | 通过 |
| 拒绝路径没有把草稿文本当普通消息发出去 | `busy=false` |

这是 P1-04 最关键的隐私性质，并且是在**真实主进程 + 真实 pi-web** 上验证的，不是文字声明。

### 3.3 text-only 模型拒绝图像任务（真实行为）

用一张**合成的真实 PNG**（8×8，180 字节）经文档化的 `prompt` 接口发送，模型在 `models.json` 中声明 `input: ["text"]`。

| 断言 | 实测 |
|---|---|
| text-only 模型**从未收到图像数据** | `providerReceivedImage=false`、`totalImagesInTranscript=0` |
| **被丢弃的图像在消息里被显式标注**，而不是静默消失 | provider 实际收到的用户消息为 `describe this synthetic image(image omitted: model does not support images)` |

第二条是**观测到的事实**，不是推测：Pi 保留了消息但在文本中标注图像被省略，因此会话记录里能看出"曾附了一张图但未被支持"，而不是假装什么都没附。

|---|---|

## 4. 正向截图路径：已在本机实测通过（41/41）

上一版记录为「未验证」，原因是当时会话没有真实前台窗口。本机已有真实桌面前台后，该路径通过**产品自身的唤醒快捷键**被完整跑通：

```
本测试自建的窗口 → 合成 Ctrl+Shift+Space（真实全局快捷键）→ 产品唤醒时记录目标
  → 用户请求截图 → 真实 desktopCapturer 按句柄捕获 → 预览 → 丢弃 / 确认 → 确认的图像送达 provider
```

### 4.1 为什么必须由测试自己创建窗口

唤醒时记录的“用户当时看的窗口”，如果就是桌面当下最前面的那个窗口，测试就会去截**用户真实窗口**（本机实测为 `pi-orb - Pi Web - Google Chrome`）。因此：

- 测试用 `evidence/p1-04/target-app/` 启动**自己的可丢弃窗口**（纯洋红底 + 两角黑色标记，标题含每次运行唯一的 nonce，**不含任何真实数据**）；
- `evidence/p1-04/wake-foreground.ps1` 只把**该测试自己创建的句柄**置于前台，再按键发送真实唤醒组合键；
- **不新增任何产品测试钩子**，不扩大权限：快捷键、记录、捕获、预览、确认全部走产品原有代码路径。

脚本首先断言**产品记录到的目标就是测试自己的窗口**（标题 + pid 双重比对），否则后续检查不再进行；这是防止误截用户真实桌面的门。

### 4.2 实测结果

| 断言 | 实测 |
|---|---|
| 测试自己的窗口能被置于前台 | 通过（`SetForegroundWindow` 返回 true 且前台句柄等于目标） |
| 合成唤醒组合键真的触发了产品的全局快捷键 | 通过（同一机制先用独立探针验证：跨进程、另一进程在前台时同样触发） |
| 唤醒记录的目标是**测试自己的窗口**，不是唤醒前的前台窗口 | 通过（标题与 pid 均匹配测试窗口） |
| 记录目标**不是** Orb 自己 | 通过 |
| 捕获成功且带真实像素 | 通过（`ok:true`、`image/png`、尺寸与窗口物理尺寸一致） |
| **截图尺寸 = 被记录窗口的物理尺寸，而不是整屏** | 通过（实测 1083×783；目标 app 用 `screen.dipToScreenRect` 自报的物理 bounds 也是 1083×783） |
| 捕获图像**不是**整屏 | 通过（1081×783 << 2560×1600） |
| 预览确实包含被记录窗口的像素 | 通过（洋红占比 **0.907**） |
| **预览不夹带 Orb 自身遮罩** | 通过（Orb 强调色 `#4c8bf5` 占比 **0**；Orb 是 always-on-top，若夹带必然出现） |
| 丢弃预览不上传任何东西 | 通过（provider 请求数不变） |
| 确认后 provider 收到**图像数据** | 通过（`type=image` 部分 1 个） |
| provider 收到的**正是预览过的那份字节** | 通过（对 base64 求 sha256，预览 hash == provider 收到 hash） |
| 确认的图像发给的是**支持图像的模型** | 通过（`p1-vision`） |

> 关于尺寸对比的修正：早期版本把捕获尺寸与**驱动上报的窗口 bounds** 比较，那描述的是驱动将要点击的框架矩形（1065×774），与捕获的物理像素（1083×783）本就不是同一矩形，会产生**假失败**。现在改为与目标 app 自报的物理 bounds 比较。

### 4.3 本次实测新发现的真实缺陷（已修复）

| 缺陷 | 后果 | 修复 |
|---|---|---|
| **构建从不拷贝原生 helper**（`out/main/native/foreground-window.ps1` 不存在） | 装机后**每次记录目标都失败**，且失败被报成“没有前台窗口”——一个缺失的构建产物伪装成了环境事实 | `electron.vite.config.ts` 在构建时按运行时解析的固定路径产出该脚本 |
| **记录失败时保留旧记录** | 与上一条叠加：启动时记录的用户真实窗口一直留存，之后点截图会**静默截取用户早已切走的窗口** | `RecordedTargetStore.record()` 失败时清空快照 |
| **收起时不清理记录** | 收起是用户实际会走的路径；隐藏后记录仍存活，因此上一行的问题在实际使用中可达 | 生命周期 `collapse` 新增 `clearRecordedTarget` |

这三条都是“单元测试全绿、仅端到端才能暴露”的类型，正因为它们才必须跑真实产品路径。

## 5. 已知设计取舍（记录以免后续误改）

| 取舍 | 原因 |
|---|---|
| 按原生句柄匹配，并要求标题仍一致 | 句柄在窗口销毁后可能被复用；标题一致不是身份证明，但能挡住"明显是另一个窗口"，而静默截取句柄的新主人更糟 |
| 超限时**拒绝**而不是缩放 | 预览必须与发送内容一致；缩放会让模型看到的像素与用户看过的不同 |
| helper 用 PowerShell（约 750 ms） | Win32 前台窗口无法从 Electron 直接读取。**P1-05 已用 Cua 驱动替换此接缝用于桌面动作**（`cua_driver_adapter` 用驱动的窗口列表 + 记录目标匹配）；截图路径仍用此 helper 记录目标 |
| **目标只记录一次，截图时不再重读前台窗口** | 这是 P1-07 修复的真实缺陷：原实现在用户点截图时**重新读取前台窗口**，而此刻焦点已在 Orb 上，重读必然失败（reader 排除自身 PID），使**正向截图路径永远拒绝**。现在由 `RecordedTargetStore` 在**唤醒/显示之前**记录一次，截图流程**消费**该记录并只校验窗口是否仍存在且标题一致。注意校验**不是**前台判定：用户已主动切到 Orb，被记录的窗口本就不在前台 |
| 陈旧确认**不消费**当前预览 | 早期实现把"不匹配"与"取消"合并，导致一次迟到的点击清掉了用户正在看的预览及其草稿消息——这是真实缺陷，已由 `screenshot-flow.test.ts` 固定 |
| 本阶段不接受自动截图 | 逐动作自动回图属 M3（P1-06），此时不能留下静默入口 |

## 6. 非破坏性确认

- 未修改 pi-web；运行脚本断言其工作树仍只有那 6 个既有改动。
- 只写本次运行目录与 `evidence/`；`HOME`/`USERPROFILE` 指向隔离目录；使用隔离测试密码。
- **只截取测试自己创建的窗口**：目标窗口由 `evidence/p1-04/target-app/` 生成，内容为纯色与两个角标，运行时标题带唯一 nonce，**不含任何真实数据**；脚本先断言产品记录到的正是它，才继续。
- **不对任何真实应用输入内容**：唯一的合成按键是唤醒组合键本身（`Ctrl+Shift+Space`），不向目标窗口键入任何字符。
- 证据中无任何图片文件；矩形轮廓仅在内存中测量后丢弃，不落盘。
- 无真实模型、无真实凭据；provider 接收到的图像仅存在于本机隔离进程的请求日志中。
